# Migrations

Every schema change is an explicit, reviewable migration. There is no ORM auto-migration anywhere in
this project (§53).

Applied with [golang-migrate](https://github.com/golang-migrate/migrate) v4.19.1, run from a
container so no local install is needed:

```bash
make migrate-up            # apply all pending
make migrate-down          # roll back the most recent
make migrate-status        # current version
make migrate NAME=add_foo  # create a new pair of files
```

## Conventions

**One global sequence**, not one per feature. Ordering across features matters — `sessions`
references `users`, so the two cannot be sequenced independently.

```
000001_users.up.sql
000001_users.down.sql
000002_sessions.up.sql
000002_sessions.down.sql
```

**Every migration has a working `down`.** Write it at the same time as the `up` and test it, because
the moment you need it is the moment you cannot afford to discover it is wrong.

**Name the file after what it does to the schema**, not after the ticket or the phase:
`000004_rooms.up.sql`, not `000004_phase4.up.sql`.

**Feature ownership still applies.** The sequence is global, but each table has exactly one owning
feature (MEMORY.md §15). A migration should touch one feature's tables; if it touches several, that
is worth a second look at whether the boundary is right.

## Rules

- **Constraints protect invariants, not just application code.** Capacity limits, uniqueness, and
  the wallet's sum-to-zero rule are enforced by the database. Application validation is the friendly
  error message; the constraint is the guarantee (§10).
- **Ledger tables are append-only.** No migration may add an `UPDATE` or `DELETE` path to
  `ledger_transactions` or `ledger_entries` (ADR 0010).
- **All timestamps are `timestamptz`, always UTC** (§56).
- **Money is `BIGINT` minor units.** No `float`, no `double precision`, ever (ADR 0010).
- **IDs are UUIDv7**, generated by the application and stored as native `uuid`. The one exception is
  `ledger_entries`, which uses `bigserial` — see ADR 0011.
- **Index deliberately.** For each index, know which query uses it, the cardinality, and the write
  cost (§54). Do not index a column because it might be useful.
- Adding an index to a large table should use `CREATE INDEX CONCURRENTLY`, which requires the
  migration to run outside a transaction.

## Status

Empty. The first migration arrives in **Phase 2** (`users`, `sessions`), because Phase 1 builds
infrastructure only and no feature owns a table yet.

Until then `make migrate-up` prints a note and exits cleanly. golang-migrate itself reports an empty
directory as `first .: file does not exist`, which reads like broken plumbing rather than "nothing
to apply", so the Makefile guards against it. That guard goes away once this directory is never
empty again.

The wiring is verified: running the container against the dev database creates the
`schema_migrations` bookkeeping table, which is how we know connectivity and credentials are right
before any real migration depends on them.
